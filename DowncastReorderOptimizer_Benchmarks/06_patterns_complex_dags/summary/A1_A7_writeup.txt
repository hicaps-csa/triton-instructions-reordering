2. A1 -- 3+ DISTINCT-KIND DIAMOND ON ONE CAT (cache scaling)
--------------------------------------------------------------------------------

What it tests: that applyMultiConsumerOptimization's dedup cache
(keyed on (OperationName, ResultType)) scales beyond two distinct
kinds. The 2-kind case (dual_quant_2d, multi_consumer_cat_2d) is
extended to THREE distinct OperationName values fanning out from one
fp32 tt.cat.

Kinds chosen (verified via TTIR probing on this Triton build):
  arith.fptosi : fp32 -> int8
  arith.truncf : fp32 -> float16
  tt.fp_to_fp  : fp32 -> float8e5  -- only path that exercises
                                     triton::FpToFpOp + getRoundingAttr

   load A (fp32)         load B (fp32)
       |                       |
   reshape                  reshape
       \__________ cat ________/
                    |
        +-----------+-----------+
        |           |           |
     fptosi      truncf       fp_to_fp           three distinct OpName
      (i8)       (fp16)       (fp8e5)
        |           |           |
     reshape    reshape      reshape
        |           |           |
     store i8   store f16    store fp8e5

OFF TTIR (relevant ops):
  %c = tt.cat %a_flat, %b_flat : tensor<16384xf32> -> tensor<32768xf32>
  %d_i8  = arith.fptosi %c : tensor<32768xf32> to tensor<32768xi8>
  %d_f16 = arith.truncf %c : tensor<32768xf32> to tensor<32768xf16>
  %d_fp8 = tt.fp_to_fp %c, rounding = rtne
                           : tensor<32768xf32> -> tensor<32768xf8E5M2>

ON TTIR:
  %c    = tt.cat ... : tensor<16384xf8E5M2> -> tensor<32768xf8E5M2>
  %c_31 = tt.cat ... : tensor<16384xf16>    -> tensor<32768xf16>
  %c_32 = tt.cat ... : tensor<16384xi8>     -> tensor<32768xi8>
  (no remaining `tt.cat ... f32`)

  - 3 distinct cache keys -> 3 distinct cat chains, no false sharing.
  - tt.fp_to_fp clone correctly retains `rounding = rtne`.

A1 perf sweep (36 configs):

  Speedup matrix at M=N=8192:

  m=64    1.00x   1.00x   1.58x

  Summary: 8 wins / 6 neutrals / 4 regressions across 36 configs.

3. A2 -- SAME-KIND, SAME-TYPE FAN-OUT (cache-HIT path)
--------------------------------------------------------------------------------

What it tests: that applyMultiConsumerOptimization's dedup cache HITS
when two consumers of the same producer share the same (OperationName,
ResultType) cache key. Until now nothing in the suite exercised this
code path -- only the cache-miss / cache-with-distinct-keys paths.

Important framing finding documented during construction:

  The textbook A2 pattern -- one fp32 tt.cat consumed by two
  `c.to(tl.float16)` calls -- does NOT reach the cache-hit code path
  in DowncastReorderOptimizer on real Triton. The frontend / canonicalize step
  folds the two identical `arith.truncf %c` ops into ONE SSA value
  BEFORE our pass runs, so the pass sees only ONE consumer of the cat
  and the cache stores a single entry. The lookup never gets to hit.

  To actually drive the cache-hit path we insert an additional mover
  layer (a reshape) between cat and each truncf, with DIFFERENT output
  shapes so the frontend cannot merge them. The pass then propagates
  each truncf up through its reshape, and only at cat do the two
  cloned truncf clones meet -- with identical (OperationName,
  ResultType) but distinct SSA values. The cache misses on the first
  and HITS on the second.

OFF TTIR:
  %c    = tt.cat %a_flat, %b_flat : tensor<16384xf32> -> tensor<32768xf32>
  %c_r1 = tt.reshape %c : tensor<32768xf32> -> tensor<256x128xf32>
  %c_r2 = tt.reshape %c : tensor<32768xf32> -> tensor<128x256xf32>
  %d1   = arith.truncf %c_r1 : tensor<256x128xf32> to tensor<256x128xf16>
  %d2   = arith.truncf %c_r2 : tensor<128x256xf32> to tensor<128x256xf16>

ON TTIR:
  %d1    = arith.truncf %a_19 : tensor<128x128xf32> to tensor<128x128xf16>
  %d1_24 = arith.truncf %b_23 : tensor<128x128xf32> to tensor<128x128xf16>
  %c     = tt.cat %a_flat, %b_flat : tensor<16384xf16> -> tensor<32768xf16>
                                                                       ^^^^^
                                       -- ONE cat-on-fp16 (cache hit)

    tile     OFF us  ON us   sp        tile     OFF us  ON us   sp
    64x64    2898.9  2886.7  1.00x     64x64     680.4   681.1  1.00x
    64x256   2358.9  2045.6  1.15x     64x256    588.1   508.5  1.16x
    128x128  2647.9  2224.3  1.19x     128x128   660.0   537.4  1.23x
    128x256 12945.1 11760.9  1.10x     128x256  3162.2  2879.7  1.10x
    256x128 11357.7  9719.7  1.17x     256x128  2773.6  2377.5  1.17x

  Summary: 7 wins / 3 neutral / 0 regressions. Best 1.23x at 128x128.

4. A3 -- MIXED-KIND, SAME-TYPE FAN-OUT (cache split)
--------------------------------------------------------------------------------

What it tests: when two consumers of a producer produce nominally the
SAME result type but via DIFFERENT OperationName values, the dedup
cache (keyed on (OperationName, ResultType)) splits them into
SEPARATE rewritten chains.

Kernel: fp32 cat fed by arith.fptosi-to-i8 AND arith.fptoui-to-i8.

Key finding from the TTIR: both fptosi and fptoui produce the SAME
MLIR result type `tensor<32768xi8>` (signless integer). The cache
key sees two entries differing ONLY in OperationName, so it
correctly produces two chains.

OFF TTIR:
  %c = tt.cat %a_flat, %b_flat : tensor<16384xf32> -> tensor<32768xf32>
  %d_i8 = arith.fptosi %c : tensor<32768xf32> to tensor<32768xi8>
  %d_u8 = arith.fptoui %c : tensor<32768xf32> to tensor<32768xi8>
                                                    ^^^^^^^^^^^^
                                                    -- SAME element type

ON TTIR:
  %c    = tt.cat ... : tensor<16384xi8> -> tensor<32768xi8>   <- fptoui chain
  %c_28 = tt.cat ... : tensor<16384xi8> -> tensor<32768xi8>   <- fptosi chain

Policy verdict: although the result types match, the *semantics* of
fptosi (signed) and fptoui (unsigned) differ for the same fp32 input.
Sharing a chain would mean ONE rewritten output would be reused for
both stores, producing the wrong bits for one of them. The current
(OperationName, ResultType) key is CORRECT for correctness.

A3 perf sweep (10 configs) -- this is the BIGGEST WIN in A2-A7:

  M=N=8192:                            M=N=4096:
    tile     OFF us  ON us    sp       tile     OFF us  ON us    sp
    64x64    2622.0  2589.0   1.01x    64x64     505.3   510.3   0.99x
    64x256   1845.8  1481.8   1.25x    64x256    462.8   375.7   1.23x
    128x128  2212.4  1790.1   1.24x    128x128   530.2   417.5   1.27x

    256x128  8912.1  2294.4   3.88x    256x128  2151.6   560.2   3.84x

  Summary: 8 wins / 2 neutral / 0 regressions. Best 4.72x at 128x256.

ncu at 128x256 (8192):
  metric        OFF         ON
  duration      9922us      2097us            (-79%, sp 4.73x)
  DRAM total    4848 MB     1020 MB           (-3828 MB saved)
  spill LD      17.24 M     0.91 M            (-95%)

5. A4 -- MULTI-LEVEL DIAMOND (cache + worklist together)
--------------------------------------------------------------------------------

What it tests: cat fans out into TWO branches, each with MORE movers
(reshape, trans+reshape) before terminating in arith.truncf-to-fp16.
The pass must reach cat ONLY after rewriting the lower movers, and
only THEN does cat see two truncf-fp16 users (which the cache then
dedups).

ON TTIR (relevant ops, post-pass + canonicalize):
  %d1     = arith.truncf %a_19 : 128x128 fp32 to fp16
  %a_flat = tt.reshape %d1 : 16384 fp16
  %d1_24  = arith.truncf %b_23 : 128x128 fp32 to fp16
  %b_flat = tt.reshape %d1_24
  %c      = tt.cat %a_flat, %b_flat : tensor<16384xf16> -> tensor<32768xf16>
                                                                          ^^^^^
                                                                          ONE cat-on-fp16
  %c1     = tt.reshape %c : 256x128 fp16
  %c2     = tt.reshape %c : 128x256 fp16
  %out2   = tt.reshape %c2 : 256x128 fp16
  -- branch 1 stores %c1 directly (trans-truncf-trans collapsed)

Two observations:
  (1) Cache hit at cat: ONE cat-on-fp16 shared by both branches.
  (2) Branch 1's trans-truncf-trans collapsed into just `c1 = reshape(c)`
      after the pass + downstream canonicalize.

A4 perf sweep (10 configs):

  M=N=8192:                            M=N=4096:
    tile     OFF us  ON us   sp        tile     OFF us  ON us   sp
    64x64    2899.8  2896.3  1.00x     64x64     680.1   681.5  1.00x
    64x256   2367.6  2040.5  1.16x     64x256    587.8   508.8  1.16x
    128x128  2636.0  2220.5  1.19x     128x128   661.1   537.5  1.23x
    128x256 12985.3 11760.1  1.10x     128x256  3157.3  2874.4  1.10x
    256x128 11392.0  9711.7  1.17x     256x128  2790.6  2371.7  1.18x

  Summary: 7 wins / 3 neutral / 0 regressions. Best 1.23x at 128x128.

Numerically near-identical to A2 -- both kernels end up with the same
cache-hit-rewritten structure (1 cat-on-fp16 + 2 downstream
reshapes), so they produce essentially the same SASS and the same
perf landscape. A4 thus confirms that multi-level chain propagation
arrives at the SAME end state as the direct cache-hit kernel; the
extra trans layer is fully absorbed by canonicalize.

6. A5 -- CAT-OF-CATS / NESTED MOVERS (worklist iteration bound)
--------------------------------------------------------------------------------

What it tests: that runOnce's worklist can rewrite a chain of THREE
nested cats from a SINGLE seed (the outer cat) in ONE sweep.

Kernel: 4 inputs, cat(a,b) and cat(c,d) feed cat(ab, cd), terminated
by truncf-fp16.

OFF: 3 cats (fp32), 1 truncf-fp16.
ON : 3 cats (fp16), 4 truncfs (one per input load), 0 fp32 cats. ALL
     in one runOnce sweep.

Single-sweep convergence VERIFIED: worklist seed = outer cat; pop
outer cat, push truncf above; re-queue inner cats; pop each, push
truncf above onto their reshape operands; pop each reshape, push
truncf above onto the load result. Five worklist pops, one runOnce.

A5 perf sweep (10 configs):

  M=N=8192:                            M=N=4096:
    tile     OFF us   ON us    sp      tile     OFF us  ON us    sp
    64x64    3514.7   3501.2   1.00x   64x64     926.8   923.6   1.00x
    64x256  18729.7   3291.4   5.69x   64x256   4625.1   838.6   5.52x
    128x128 18214.0   3298.6   5.52x   128x128  4476.5   862.3   5.19x
    128x256 18701.4  20954.9   0.89x   128x256  4557.6  5098.4   0.89x
    256x128 18234.3  19451.2   0.94x   256x128  4456.0  4753.3   0.94x

  Summary: 4 wins / 2 neutral / 4 regressions. Best 5.69x at 64x256.

A5 has the largest speedup in the bundle (5.69x) AND four
regressions. Mechanism: with 3 cats and 4 cloned truncfs after the
pass, the per-chain register pressure varies dramatically with tile
size.

ncu at the regr config 128x256 (8192) shows OFF and ON essentially
equal in single-launch capture (same spill, regs, DRAM bytes), while
the nsys 100-launch average shows a 0.89x regression. Possible
causes: ncu's --launch-skip 5 captures a post-warmup launch; or
ncu's kernel-replay measures a stable-state launch. The nsys
multi-launch average is the more reliable headline; the steady-state
ncu telemetry suggests no per-launch register/spill change, so the
regression must live in launch-overhead or warmup variance.

7. A6 -- PER-OPERAND BITWIDTH GUARD
--------------------------------------------------------------------------------

What it tests: the per-operand bitwidth guard in eligibleReducers
(DowncastReorderOptimizer.cpp:356-372) skips the consumer when ANY operand's
element-type bitwidth is NOT STRICTLY GREATER than the consumer's
destination bitwidth.

Two code paths in one kernel:
  Path A:   load fp16 -> reshape -> arith.fptosi-to-i16
            operand bitwidth 16, dest bitwidth 16  -- NOT strictly >
            -> guard FAILS, pass should NOT rewrite.
  Path B:   load fp32 -> reshape -> arith.fptosi-to-i16
            operand bitwidth 32, dest bitwidth 16  -- STRICTLY >
            -> guard PASSES, pass should rewrite.

OFF TTIR (both paths):
  Path A:  %a16_flat = tt.reshape %a16 : f16 -> f16
           %pa = arith.fptosi %a16_flat to i16
  Path B:  %a32_flat = tt.reshape %a32 : f32 -> f32
           %pb = arith.fptosi %a32_flat to i16

ON TTIR:
  Path A:  UNCHANGED -- guard correctly fails for fp16->i16
  Path B:  %pb = arith.fptosi %a32 to 128x128xi16
           %a32_flat = tt.reshape %pb
           -- fptosi pushed ABOVE the reshape

The TWO paths in the SAME kernel give a single-shot proof.

A6 perf sweep (10 configs):

  M=N=8192:                            M=N=4096:
    tile     OFF us  ON us   sp        tile     OFF us  ON us   sp
    64x64    1611.1  1613.1  1.00x     64x64     385.4   386.1  1.00x
    64x256   1251.0  1251.0  1.00x     64x256    315.9   315.9  1.00x
    128x128  1307.5  1307.1  1.00x     128x128   327.7   328.3  1.00x
    128x256  4288.1  4283.4  1.00x     128x256  1025.3  1025.9  1.00x
    256x128  3820.1  3819.5  1.00x     256x128   921.1   921.7  1.00x

  Summary: 0 wins / 10 neutral / 0 regressions.

10 out of 10 configs are PERFECTLY neutral (within 0.5%). SASS-level
check confirms identical opcode counts (F2I=256, LDG=48 in both
states). The "negative-control" experiment for the bundle: showing
the pass is a perf no-op when it correctly skips.


--------------------------------------------------------------------------------
8. A7 -- Y-SHAPE UPSTREAM (CSE interaction)
--------------------------------------------------------------------------------

What it tests: a SHARED fp32 load feeding TWO mover -> truncf chains.
The pass rewrites each chain independently, so the load result ends
up with TWO redundant truncf consumers (identical operand, identical
result type). Does downstream MLIR CSE catch the duplication?

Kernel:
  a = load fp32 (shared SSA value)
  branch 1: trans(a) -> truncf-fp16 -> trans (back)
  branch 2: reshape(a) -> truncf-fp16 -> reshape (back to 2D)

OFF TTIR:
  %a_t   = tt.trans %a_20  : fp32
  %d1    = arith.truncf %a_t   : fp16
  %a_r   = tt.reshape %a_20  : 16384xf32
  %d2    = arith.truncf %a_r   : 16384xf16
  -- TWO truncf ops, different operands

ON TTIR:
  %d1    = arith.truncf %a_20 : fp16   -- ONE truncf
  %a_r   = tt.reshape %d1     : 16384xf16
  %out2  = tt.reshape %a_r    : 128x128 fp16
  -- both stores consume %d1; branch 1's trans-trans collapsed

TTGIR:  OFF 2 truncf  ->  ON 1 truncf   (CSE catches it)
SASS :  OFF F2F=128   ==  ON F2F=128    (identical)

A7 perf sweep (10 configs): 0 wins / 10 neutral / 0 regressions.
Identical SASS in both states.

CSE pipeline interaction VERIFIED: the pass safely produces
redundant truncfs in the Y-shape pattern; downstream MLIR
canonicalize/CSE de-duplicates exactly. No new code needed in
DowncastReorderOptimizer.

10. WHAT A1-A7 ADD TO THE STORY
--------------------------------------------------------------------------------

  (1) Cache SCALING proven (A1): the dedup cache scales from 2 to 3
      distinct (OperationName, ResultType) keys with no false
      sharing. Pass produces 3 typed cats from 3 distinct reducer
      kinds. First end-to-end test of the triton::FpToFpOp clone
      branch (including rounding-mode preservation) and first fp8
      output in the suite.

  (2) Cache HIT path empirically verified for the first time (A2 +
      A4): it is reached during multi-level chain propagation, NOT
      for naive textually-duplicated reducers (the frontend
      pre-merges those). A2's 1.22x win comes through the cache hit
      path explicitly.

  (3) Cache SPLIT verified correct (A3): two different OpName values
      with the same MLIR result type get separate chains, which is
      the right policy because their semantics differ (signed vs
      unsigned int conversion). A3's 4.72x win is the largest in
      the bundle.

  (4) Multi-level worklist propagation verified (A4 + A5): the pass
      reaches deep producers in ONE runOnce sweep via correct
      upstream-mover re-queueing. A4 demonstrates trans-truncf-trans
      pattern absorbed by canonicalize; A5 demonstrates 3-cat nested
      mover narrowing in 5 worklist pops.

  (5) Per-operand bitwidth guard verified (A6): correctly skips
      consumers where any operand bitwidth is not strictly greater
      than dest. Two paths in one kernel give simultaneous proof.

A1-A7 close all seven DAG-topology gaps in DowncastReorderOptimizer's test
coverage. A1 extends the dedup cache from 2 to 3 distinct
(OperationName, ResultType) keys with no false sharing, and is the
first kernel to exercise the triton::FpToFpOp clone branch

two-identical-truncf pattern fails because the frontend pre-merges
identical reducers before our pass runs). A3 verifies the cache

result types, and produces the largest single-kernel speedup in the
study (4.72x at 128x256, 101% DRAM-model explained). A4 shows
multi-level chain propagation converging to the same end state as
A2's direct cache hit. A5 demonstrates worklist single-sweep
convergence on 3 nested cats with 5.69x win and corresponding
regressions. A6 confirms the per-operand bitwidth guard correctly
skips on equal-bitwidth and fires on strictly-greater bitwidth, both
within the same kernel. A7 confirms downstream MLIR CSE de-
duplicates the pass's redundant truncf clones, leaving SASS
unchanged. The DRAM-bandwidth model from speedup_explaination.txt
generalizes from {single-chain linear, 2-chain diamond} to
{3-chain diamond, cache-hit diamond, mixed-kind diamond} spanning a
