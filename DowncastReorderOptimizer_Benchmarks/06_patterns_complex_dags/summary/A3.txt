--------------------------------------------------------------------------------
1. WHAT A3 TESTS
--------------------------------------------------------------------------------

A3 is one of the seven DAG-topology gaps in future_experiments.txt.
When two consumers of a producer produce nominally the SAME result type
but via DIFFERENT OperationName values, the dedup cache (keyed on
(OperationName, ResultType)) splits them into SEPARATE rewritten
chains.

The policy question A3 raises: should arith.fptosi and arith.fptoui
share a chain when they produce the same MLIR result type? Currently
the cache distinguishes them because the key includes OperationName.

Kernel: fp32 cat fed by:
  arith.fptosi -> int8
  arith.fptoui -> uint8

   load a (fp32)         load b (fp32)
       |                       |
   reshape                  reshape
       \\__________ cat ________/                 <- fp32 cat
                    |
            +-------+-------+
            |               |
         fptosi           fptoui           <- different OpName,
         (i8)             (u8)                same i8 result type
            |               |
         store i8         store u8


--------------------------------------------------------------------------------
2. STRUCTURAL PROOF (TTIR)
--------------------------------------------------------------------------------

OFF TTIR:
  %c    = tt.cat %a_flat, %b_flat : tensor<16384xf32> -> tensor<32768xf32>
  %d_i8 = arith.fptosi %c : tensor<32768xf32> to tensor<32768xi8>
  %d_u8 = arith.fptoui %c : tensor<32768xf32> to tensor<32768xi8>
                                                    ^^^^^^^^^^^^
                                                    -- SAME element type

ON TTIR:
  %c    = tt.cat ... : tensor<16384xi8> -> tensor<32768xi8>   <- fptoui chain
  %c_28 = tt.cat ... : tensor<16384xi8> -> tensor<32768xi8>   <- fptosi chain
  -- TWO i8 cats, one per OperationName

Both fptosi and fptoui produce the SAME MLIR result type
`tensor<32768xi8>` (signless integer). The cache key sees two
entries differing ONLY in OperationName.


--------------------------------------------------------------------------------
3. POLICY VERDICT
--------------------------------------------------------------------------------

Although the result types match, the SEMANTICS of fptosi (signed) and
fptoui (unsigned) DIFFER for the same fp32 input. Sharing a chain
would mean ONE rewritten output would be reused for both stores,
producing the WRONG bits for one of them. The current
(OperationName, ResultType) key is CORRECT for correctness -- not a
missed sharing opportunity. The cache split is NECESSARY, not a
sub-optimal policy.


--------------------------------------------------------------------------------
4. BIT-EXACT VERIFICATION
--------------------------------------------------------------------------------

verify_all.sh ran A3 OFF and ON at (M, N, BM, BN) = (2048, 2048, 128, 128).
Both outputs (out_i8, out_u8) bit-identical across OFF/ON. Combined
SHA-256 matches.

The OFF kernel runs in a high-occupancy / 64-reg / heavy-spill
regime (31M spill reqs). The pass narrows both chains to i8 (4x
narrowing each), the cloned chains fit in 255 regs at low
occupancy, spill collapses, DRAM bytes drop 80%.
