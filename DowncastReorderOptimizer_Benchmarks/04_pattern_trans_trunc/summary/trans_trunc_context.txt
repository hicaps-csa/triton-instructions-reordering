WHAT THE PRIOR SESSION ESTABLISHED (recap; see ../SESSION_CONTEXT.txt)
-------------------------------------------------------------------------------
  DowncastReorderOptimizer pulls size-reducing element-wise ops (truncf, fptosi,
  fptoui, narrowing index_cast) BEFORE data-movement ops (cat, trans,
  broadcast). It was validated on cat_quant_spill_baseline (fp32 cat ->
  int8 truncate) where it produced a 2.7x speedup at the spill cliff
  (m*n=32768) by keeping a truncated working set in registers. At larger
  blocks both versions spilled and the pass was neutral or slightly
  negative.

  Twelve fixes were applied to DowncastReorderOptimizer.cpp (validation, fixed-point
  iteration, multi-consumer dedup, error handling, debug logging,
  module-level verify, etc.). The pass is correct and semantics-
  preserving on cat -> truncate.

  Open question heading into this session: does DowncastReorderOptimizer also help on
  the trans -> truncate pattern that the user opened transtruncnew.py to
  explore?

WHY THE PASS DOES NOTHING HERE (vs cat_quant winning)
-------------------------------------------------------------------------------
  tl.trans on a register-resident tile is a logical layout permutation,
  not a memory data movement. Bit-width at the trans step doesn't change
  register-allocation decisions or live-range structure: the same number
  of bytes are permuted in place. By the time the IR-level pass would
  have shrunk anything, ptxas has already chosen the same allocation
  either way -- so the LLVM-IR conversion produces identical sequences.

  tl.cat is structurally different: it DOUBLES tile size at a specific
  point in the IR. Pulling truncate before tl.cat keeps the doubled
  tile in 8-bit form (fits in registers) instead of 32-bit (spills).
  That is a register-pressure shift the back end cannot undo, which
  is why cat_quant got a 2.7x win at the spill cliff.

  tl.trans does not have that property. Do not extend the pass to try
  to "cover" trans without first finding a pattern where the rewrite
  changes the lowering -- this kernel proved it does not.
