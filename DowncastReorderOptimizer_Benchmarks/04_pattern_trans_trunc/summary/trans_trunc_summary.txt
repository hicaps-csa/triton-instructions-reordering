KERNEL UNDER TEST
-------------------------------------------------------------------------------
  trans_trunc_fused_kernel: single fused kernel that
    1. loads a [BLOCK_M, BLOCK_N] FP32 tile,
    2. transposes it via tl.trans (-> [BLOCK_N, BLOCK_M]),
    3. casts to FP16 via .to(tl.float16),
    4. stores the result.

  TTIR pattern targeted by DowncastReorderOptimizer:
    OFF: tt.trans  : tensor<BMxBNxf32> -> tensor<BNxBMxf32>
         arith.truncf : tensor<BNxBMxf32> -> tensor<BNxBMxf16>
    ON:  arith.truncf : tensor<BMxBNxf32> -> tensor<BMxBNxf16>
         tt.trans  : tensor<BMxBNxf16> -> tensor<BNxBMxf16>

  Matrix used for measurements: square M = N = 5793 (M*N = 33,558,849
  ~= 2^25), fp32 input, fp16 output, contiguous strides.

CORRECTNESS (pre-perf check)
-------------------------------------------------------------------------------

    - Deterministic seed (default 0).
    - Independent fresh TRITON_CACHE_DIR per pass state.
    - Compute torch reference: src.T.contiguous().to(torch.float16).
    - SHA256 of dst tensor (raw bytes).

  7 (M, N, BLOCK_M, BLOCK_N) configurations exercised square + non-square
  shapes, with block tiles spanning 32x32 to 128x128. All produced:

    OFF SHA256 == ON SHA256 == SHA256(torch.ref)
    bit-exact match in every cell, max |dst - ref| = 0.0

  Conclusion: DowncastReorderOptimizer is semantics-preserving on the trans -> truncf
  pattern across all tested shapes.

INTERPRETATION
-------------------------------------------------------------------------------
  1. The pass is a no-op at the SASS level for this kernel.
     Three independent confirmations:
       (a) PTX bit-identical for all 16 block configs.
       (b) cubin bit-identical for all 16 block configs.
       (c) ncu hardware counters identical (registers, occupancy,
           throughput, duration, spill loads/stores) for all 3 sampled
           block configs.

  2. Why the pass does nothing here:
     The TTIR rewrite is real and survives TTGIR, but the TTGIR -> LLVM
     IR conversion already produces optimal code for the trans + truncf
     chain regardless of source-IR order. tl.trans on a register-resident
     tile is a logical layout permutation, not a memory data movement;
     bit-width at the trans step has no effect on register-allocation
     decisions or spill behavior. By the time DowncastReorderOptimizer would shrink
     the working set, ptxas / Triton register allocation has already
     decided where to spill.

  3. Why cat_quant won and trans_trunc does not:
     tl.cat doubles tile size at a specific point in IR. Pulling truncf
     before tl.cat keeps the doubled tile in 8-bit form (fits in regs)
     instead of 32-bit form (spills). That is a structural register-
     pressure shift that the optimizer cannot undo on its own.

     tl.trans does not change tile size or live-range structure -- it
     permutes the same number of bytes in place. Truncating before vs
     after produces equivalent live ranges, and the back end picks the
     same allocation either way.

  4. Performance is dominated by block-shape, not by the pass.
     Within OFF (or within ON), best/worst configs differ by ~10x:
       64x128  -> 386 us  (88 regs, no spills, 60% occupancy, 79% DRAM)
       256x64  -> 4072 us (255 regs, heavy spills, low occupancy)
     Future tuning effort should target tile-shape selection, not the
     trans -> truncf rewrite.
