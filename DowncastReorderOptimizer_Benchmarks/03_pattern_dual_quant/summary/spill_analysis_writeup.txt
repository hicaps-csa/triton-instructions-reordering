================================================================================
  dual_quant_2d @ M=N=8192 -- WIN (128x128) AND REGR (128x256)
  Spill-removal pass: verification, attribution, and the regression case
================================================================================

What the kernel computes:
  load a, b (fp32, MxN)
       -> reshape to 1-D
       -> tl.cat into a 1-D fp32 vector of length 2*BLOCK_M*BLOCK_N
       -> DIAMOND: this single cat feeds two reducers
            (1) c.to(int8)   -> reshape -> store i8
            (2) c.to(float16)-> reshape -> store f16
  Two outputs per launch: (2M, N) int8 AND (2M, N) fp16.

What the pass does (DAG extension A):
  Clones BOTH reducer chains backward through the cat. Because both users
  are size-reducing (i8 and f16 are smaller than fp32), the guard does
  NOT bail. The dedup cache keyed on (OperationName, Type) distinguishes
  (fptosi, i8) from (truncf, f16), so we get TWO rewritten chains. The
  original fp32 cat dies (use_empty after rewrites).

  Intent: avoid materializing the large fp32 cat working set; instead
  run two narrower chains in i8 and f16.

  Risk: if the cloned chains still cannot fit in registers, BOTH chains
  spill independently and you pay 2x the spill cost plus duplicated
  arithmetic. That is exactly what happens at REGR (128x256).

================================================================================
6.  INSTRUCTION-COUNT ACCOUNTING (per warp)
================================================================================

  WIN: per-warp inst delta = -3,571,712 / (4096 blocks * 4) = -218 inst/warp
       SASS predicts:
         removed: 244 spill ops + 32 BAR + 16 LDSM + 16 STS + ~5 LOP3   = 313
         added  : 320 PRMT + 138 IMAD.MOV                               = 458
         net    : +145 (ADDED)  -- but ncu shows -218
       Why the mismatch? SASS counts STATIC instructions; ncu counts
       DYNAMIC issued instructions. Spill ops are predicated and can
       execute fewer times than statically present; ALSO many of the
       "added" IMAD.MOV.U32 may be predicated off in most threads. The
       net dynamic effect is fewer issued instructions because spill
       traffic carries a high dynamic cost (extra LSU pipe cycles).
       For attribution purposes, the dominant effect at WIN is still
       DRAM bandwidth saved (83%), not raw inst count.

  REGR: per-warp inst delta = -14,827,520 / (2048*4) = -1810 inst/warp (added)
        Same SASS-vs-dynamic mismatch in the other direction:
        more spill ops + more PRMT + more IMAD.MOV -> ~+1.8K dynamic
        inst per warp. Matches the SASS direction (+1618 spill +643 PRMT
        +393 IMAD.MOV - 64 BAR - 64 LDSM/STS).


================================================================================
7.  WHY DOES THE PASS REGRESS AT (128, 256)?
================================================================================

The pass's guard checks "are both users size-reducing?" but does NOT
check "will the cloned chains still fit in registers?"

At (128, 256):
  - tile = 32,768 elements
  - OFF version compiles to 64 registers (Triton chose low-reg config)
    and ALREADY spills 834 slots / 32.2M dynamic reqs
  - ON version clones the two reducer chains:
      * each clone has its own working set
      * still 64 registers
      * now each chain spills independently
      * total: 1238 slots / 40.8M dynamic reqs (+27%)
  - The duplicated arithmetic (PRMT 2x, IMAD.MOV 2.5x) adds 14.8M more
    issued instructions
  - DRAM traffic grows by 1.15 GB (28%)
  - Wall-clock penalty: 4708 us (1.47x slowdown)

Compare WIN (128, 128):
  - tile = 16,384 elements (HALF the REGR working set)
  - OFF version uses 255 registers (the cap) and spills only 64 slots
    / 2.8M dynamic reqs
  - ON version uses 255 registers and ELIMINATES all spills
  - The chain duplication still happens (PRMT 2x, IMAD.MOV +138), but
    eliminating spill bandwidth dominates.

The decisive variable is "can the cloned chain fit in registers without
spilling?". WIN (tile 16K) yes, REGR (tile 32K) no.

A correct cost model for this pass would:
  - estimate per-chain register pressure post-clone
  - require BOTH cloned chains to fit, OR estimate net spill traffic
    before vs after, and bail when after > before

The "DRAM bytes saved at ON's rate" model:
  - explains 83-84% of wall-time delta in 3 of 4 wins
  - explains 58% of the slowdown in the regression case
  - works in BOTH directions (positive delta = speedup, negative = slowdown)
  - is the single most predictive variable across all configs

dual_quant REGR is the first config where the pass NET INCREASES DRAM
bytes. It is also the first config where the pass NET REGRESSES wall time.
That is not coincidence -- the same mechanism (spill DRAM bandwidth)
governs both.


================================================================================
10. DETERMINISM ANALYSIS
================================================================================

DETERMINISTIC for both WIN and REGR:
  - Bit-exact correctness (sha256 for both i8 and f16 outputs).
  - Same algorithmic global I/O (LDG/STG/F2I/F2F identical in SASS).
  - Same launch config.
  - Spill reqs delta in SASS direction matches ncu measurement.
  - DRAM-saved time explains majority of wall delta (83% WIN, 58% REGR).
  - REGR has measurable, reproducible mechanism (clone -> double spill).

  Crucially, NEUTRAL is a clean control:
    - Identical DRAM bytes OFF vs ON (937.0 vs 937.1 MB)
    - Inst count differs (36M vs 40M) but no spill, no time delta
    - sha256 match -- pass is value-preserving
  The pass introduces neither speedup nor slowdown when there is no spill
  to manipulate.

INFERENTIAL still:
  - The exact split between "extra spill bytes" and "extra cloned-chain
    arithmetic" in REGR's residual 42%. They are coupled (more
    arithmetic -> more pressure -> more spill).
  - The exact partition between BAR/LDSM/STS reductions in WIN's residual
    17%.

But the headline causal claim is solidly supported by the regression
case: the pass's mechanism is spill-DRAM bandwidth manipulation, and when
that bandwidth goes the wrong way (REGR), wall time goes the wrong way
in proportion.


================================================================================
11. RECOMMENDED FIX FOR THE REGRESSION
================================================================================

Add a cost-model guard before applying the rewrite at REGR-shaped configs:

  precondition (current): both users size-reducing
  precondition (proposed, additional):
    estimated_post_clone_regs_per_chain <= reg_cap
    OR
    estimated_post_clone_spill_bytes < estimated_pre_clone_spill_bytes

The simplest concrete heuristic that would have caught REGR:
  if OFF spill_bytes > some_threshold AND tile_size > some_threshold:
      bail (don't clone)
Tuning thresholds against the sweep table would prevent the 4 regressions
seen in dual_quant nsys (128x256, 256x128, plus their 4096x4096 twins).
