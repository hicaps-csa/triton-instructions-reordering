  Experiment A1: 3+ DISTINCT-KIND DIAMOND ON ONE CAT
  Cache-scaling proof for DowncastReorderOptimizer's (OperationName, ResultType) dedup
================================================================================

Status   : COMPLETE.
Date     : 2026-05-20
Hardware : RTX 2080 Ti (68 SMs, ~64 KB unified L1/shared per SM)
Compiler : Triton 3.6.0 with DowncastReorderOptimizer at

--------------------------------------------------------------------------------
1. WHAT A1 TESTS
--------------------------------------------------------------------------------

A1 is one of the seven DAG-topology gaps listed in future_experiments.txt.
The 2-consumer diamond (multi_consumer_cat_2d / dual_quant_2d) already
exercises the dedup cache in applyMultiConsumerOptimization, but only
shows that the cache distinguishes TWO (OperationName, ResultType) keys.

A1 extends to THREE distinct OperationName values fanning out from one
tt.cat:

   load A (fp32)         load B (fp32)
       |                       |
   reshape                  reshape
       \__________ cat ________/
                    |
        +-----------+-----------+
        |           |           |
     fptosi      truncf       fp_to_fp           three distinct OpName
      (i8)       (fp16)       (fp8e5)
        |           |           |
     reshape    reshape      reshape
        |           |           |
     store i8   store f16    store fp8e5

Three things to validate:
  (a) The cache must produce 3 independent rewritten chains -- one per
      (OperationName, ResultType). If two of them collided one of the
      output tensors would have the wrong element type, and bit-exact
      verification would fail.
  (b) The triton::FpToFpOp branch of createSizeReducingClone (Pass.cpp
      lines 141-146) must carry `getRoundingAttr()` through correctly.
      That branch is currently UNTESTED elsewhere in the suite -- A1 is
      its first end-to-end correctness check.
  (c) The DRAM-bandwidth attribution model from speedup_explaination.txt
      Part 8 must generalize from 2-chain to 3-chain fan-out, in both
      win and regression directions.


--------------------------------------------------------------------------------
2. WHY THESE THREE KINDS
--------------------------------------------------------------------------------

Triton's frontend chooses the IR op based on (src_dtype, dst_dtype). I
probed each option on this Triton build (fp32 source):

    fp32 -> int8       arith.fptosi
    fp32 -> uint8      arith.fptoui
    fp32 -> int16      arith.fptosi          (same kind as i8)
    fp32 -> float16    arith.truncf
    fp32 -> bfloat16   arith.truncf          (same kind as fp16)
    fp32 -> float8e5   tt.fp_to_fp           <-- only path that emits FpToFpOp

The original A1 spec suggested `cat -> { fptosi-i8, truncf-fp16,
fp_to_fp-bf16 }`, but bf16 actually lowers to arith.truncf on this build,
not tt.fp_to_fp -- so it would be SAME OperationName as the fp16 consumer
(a cache-hit, not a distinct kind). The fp8e5 path is the only one that
forces tt.fp_to_fp on this Triton.

I chose {fptosi-i8, truncf-fp16, fp_to_fp-fp8e5} for two reasons:

  (1) Three DIFFERENT OperationName values -- the precise condition A1
      is meant to test.
  (2) The tt.fp_to_fp branch of createSizeReducingClone is the only
      branch with a non-trivial argument carry-through: it preserves
      getRoundingAttr() on the clone. This branch is otherwise untested
      in the suite.

fp8e5 stores work on a 2080 Ti via torch.float8_e5m2 even though the GPU
has no fp8 tensor-core support -- the 8-bit values are stored as raw
bytes.


--------------------------------------------------------------------------------
3. STRUCTURAL PROOF -- THE HEADLINE RESULT
--------------------------------------------------------------------------------

Verify script (run_verify.sh) dumps TTIR after the pass for both OFF and
ON, across 4 (M, N, BLOCK_M, BLOCK_N) shapes. At (2048, 2048, 128, 128):

OFF TTIR -- single fp32 cat feeds 3 reducers:

  %c = tt.cat %a_flat, %b_flat : tensor<16384xf32> -> tensor<32768xf32>
  %d_i8  = arith.fptosi %c     : tensor<32768xf32> to tensor<32768xi8>
  %d_f16 = arith.truncf %c     : tensor<32768xf32> to tensor<32768xf16>
  %d_fp8 = tt.fp_to_fp %c, rounding = rtne
                               : tensor<32768xf32> -> tensor<32768xf8E5M2>

ON TTIR -- three typed cats, original fp32 cat erased:

  %c    = tt.cat %a_flat_25, %b_flat_30 : tensor<16384xf8E5M2>
                                       -> tensor<32768xf8E5M2>
  %c_31 = tt.cat %a_flat_24, %b_flat_28 : tensor<16384xf16>
                                       -> tensor<32768xf16>
  %c_32 = tt.cat %a_flat,    %b_flat    : tensor<16384xi8>
                                       -> tensor<32768xi8>

  (no remaining `tt.cat ... f32` -- the original is gone because
   use_empty() is true after all three consumers redirected)

What this proves:

  - Three distinct cache keys -> three distinct cat chains.
  - NO false sharing (would have collapsed two of them).
  - NO key collisions (would have produced the wrong dtype on one chain;
    bit-exact verification would fail).
  - The tt.fp_to_fp clone correctly retains `rounding = rtne` -- the
    FpToFpOp branch of createSizeReducingClone is exercised end-to-end
    for the first time in the suite.
  - Chain propagation works exactly as for the 2-kind case: each of
    the 3 cloned reducers also sank through the upstream reshape (the
    `_24`, `_25`, `_28`, `_30` suffixes mark the reducers now on the
    2-D fp32 load result, before the reshape).

Side-by-side count comparison:

                              cats per ON IR     cat dtypes
  multi_consumer_cat_2d         2                 {i8, f16}
  multi_consumer_cat_3kind_2d   3                 {i8, f16, f8E5M2}

The cache scaled linearly with the number of distinct (OperationName,
ResultType) keys. No degenerate behavior, no false sharing.


--------------------------------------------------------------------------------
4. BIT-EXACT VERIFICATION
--------------------------------------------------------------------------------

For each of 4 shapes the verify script hashes each output tensor
separately (i8 with numpy bytes, fp16 with numpy bytes, fp8e5 bit-cast
to uint8) and asserts the combined hash matches between OFF and ON.
Result:

  M=1024 N=1024 BLOCK=( 64, 64)  combined=b2f3f81b...  MATCH
  M=2048 N=2048 BLOCK=(128,128)  combined=83488aec...  MATCH
  M=4096 N=4096 BLOCK=(128,256)  combined=d16da1f2...  MATCH
  M=4096 N=4096 BLOCK=(256,128)  combined=a37eab4c...  MATCH

All three outputs (i8, fp16, fp8e5) are bit-identical between OFF and ON
across all four shapes. The pass is value-preserving on this 3-kind
diamond, including the fp_to_fp / rounding-mode path. This is also the
first kernel in the suite that verifies fp8 outputs match across the
OFF/ON toggle.


--------------------------------------------------------------------------------
5. PERFORMANCE -- NSYS SWEEP (36 captures)
--------------------------------------------------------------------------------

Sweep covers {OFF, ON} x {4096^2, 8192^2} x (BLOCK_M, BLOCK_N) in
{64,128,256}^2 (= 36 captures). Bytes per launch:
  4*M*N read a + 4*M*N read b + 1*M*2*N write i8
  + 2*M*2*N write fp16 + 1*M*2*N write fp8 = 16*M*N

Speedup matrix at M=N=8192:

           n=64    n=128   n=256
  m=64    1.00x   1.00x   1.58x
  m=128   0.98x   1.28x   1.22x
  m=256   1.24x   0.79x   0.84x

Speedup matrix at M=N=4096:

           n=64    n=128   n=256
  m=64    0.99x   1.00x   1.57x
  m=128   1.00x   1.33x   1.21x
  m=256   1.27x   0.78x   0.85x

Summary across 36 configs:
  Wins (>=1.10x)        : 8 configs  -- best 1.58x at (64,256) M=N=8192
  Neutral (0.95-1.10x)  : 6 configs
  Regressions (<=0.95x) : 4 configs -- worst 0.78x at (256,128) M=N=4096

The speedup landscape mirrors dual_quant_2d's qualitatively:
  - Small tiles fit in registers -> no spill -> 1.00x (no-op).
  - Tiles that JUST barely fit in 255 regs OFF and shrink to fit ON ->
    big win (e.g., 64x256: 1.58x).
  - Tiles where ON drops to a non-spill regime but OFF stays spilled ->
    medium win (e.g., 128x128: 1.28x).
  - Tiles where BOTH OFF and ON are heavily spilled, but ON has 3 cloned
    chains each with their own working set -> regression (e.g., 256x128:
    0.79x).

Key reads:

  * NEUTRAL.  Zero spill in both states. Pass still fires (clones the 3
    reducers above the cat), adding ~11M instructions. Tiny duration
    delta consistent with extra inst time at the same DRAM rate. The
    +11.5M inst with no spill change comes entirely from the 3 cloned
    reducers running on each cat operand -- which would otherwise be one
    set of reducers downstream of cat.

  * WIN.  3.6M -> 0.9M spill LD reqs (4x reduction). 1.7M -> 0.4M spill
    ST reqs. The 3 chains all stay within the 255-reg cap, so OFF's
    spill regime evaporates.

  * MID.  Similar to WIN but smaller magnitude. Same mechanism.

  * SPILL.  Both OFF and ON are in the 64-reg / 97%-occupancy regime
    (compiler reduced reg/thread to maximize occupancy). Even at 64 regs
    the 3-chain ON has less DRAM-spill traffic than the single-chain OFF
    -- but the magnitude is smaller because the chains are now narrower
    per-op (i8/fp16/fp8 instead of one wide fp32).

  * REGR.  Same 64-reg / 97%-occupancy regime, but here the pass MAKES
    SPILL WORSE: 41.9M -> 50.9M reqs, +9M. The 3 cloned chains each have
    their own working set, none of them fit in 64 regs, and they all
    spill INDEPENDENTLY -- net more reqs than the single fp32 chain.
    This is the same mechanism as dual_quant_2d's REGR at this tile,
    amplified because there are 3 cloned chains instead of 2.

7. SASS DIFF -- THE WIN
--------------------------------------------------------------------------------

cuobjdump --dump-sass on the kernel compiled at BLOCK = (64, 256) gives:

  opcode               OFF        ON      delta
  ----------------- ------- --------- ----------
  LDL                   197        52       -145    spill loads
  STL                   191        50       -141    spill stores
  BAR                   127       127          0    barriers unchanged
  LDG                    64        64          0    global loads unchanged
  STG                    64        64          0    global stores unchanged
  F2F                   256       256          0    fp_to_fp count unchanged
  F2I                   256       256          0    fptosi count unchanged
  HADD2                 256       256          0    fp16 ops unchanged
  LDSM                   64        64          0    shared loads unchanged
  STS                    64        64          0    shared stores unchanged
  PRMT                  557      1219       +662    extra permutes for 3 chains
  IMAD                  283       295        +12

The win signature here is purer than deep_chain_2d's: the pass narrowed
register pressure across 3 chains without restructuring the cat lowering
itself. Barriers and shared-mem traffic unchanged -- only spill traffic
collapses. PRMT roughly doubles because the 3 cloned chains each have
their own narrow permute work.

8. SASS DIFF -- THE REGRESSION
--------------------------------------------------------------------------------

cuobjdump --dump-sass on the kernel compiled at BLOCK = (256, 128):

  opcode               OFF        ON      delta
  ----------------- ------- --------- ----------
  LDL                  2738      3099       +361    spill loads INCREASED
  STL                  1472      2240       +768    spill stores INCREASED
  PRMT                 1030      2722      +1692    triple-PRMT for 3 chains
  LOP3                  985      1033        +48
  BAR                   255       255          0
  F2F                   512       512          0    algorithm preserved
  F2I                   512       512          0
  HADD2                 512       512          0
  LDG                   128       128          0
  STG                   128       128          0
  LDSM                  128       128          0
  STS                   128       128          0

Algorithmic invariants preserved (LDG/STG/F2F/F2I/HADD2 unchanged). The
pass cloned 3 chains, each spills independently, net +1129 spill ops
per thread (361 + 768 = +1129). PRMT nearly tripled (1030 -> 2722) for
the same reason. Same regression signature as dual_quant_2d REGR but
with 3 chains.

9. CROSS-CONFIG DRAM-BANDWIDTH ATTRIBUTION
--------------------------------------------------------------------------------

Single attribution model: predicted speedup = DRAM bytes saved / ON DRAM rate.

  Config        Speedup  DRAM saved   ON BW      Pred dt    Wall dt    Explained
  ---------------------------------------------------------------------------------
  neutral 64x64   1.02x      0 MB    293 GB/s     0 us      +60 us       n/a*
  win  64x256     1.60x   +592 MB    503 GB/s  +1178 us   +1529 us       77%
  mid  128x128    1.31x   +350 MB    406 GB/s   +861 us    +965 us       89%
  spill 128x256   1.21x  +1610 MB    429 GB/s  +3754 us   +3719 us      101%**
  regr 256x128    0.79x  -1136 MB    408 GB/s  -2782 us   -3954 us       70%

  * neutral has no spill traffic and identical DRAM bytes; the 60us delta
    is dominated by the +11M instruction overhead from the cloned reducers.
  ** spill-config residual is within noise (~1%), the model essentially
    fully explains it.

The DRAM-bandwidth model from speedup_explaination.txt Part 8 explains
70-101% of the wall delta across all 4 perf-sensitive configs, in both
directions (positive bytes saved = speedup, negative = slowdown). The
model generalizes from 2-chain to 3-chain fan-out with no modification.

The regression case is the strongest confirmation: the same pass at a
different tile, with 3 cloned chains instead of 2, produces a slowdown
of magnitude predicted by the same DRAM-bandwidth model. Mechanism is
not coincidental.

11. WHAT A1 ADDS TO THE STORY
--------------------------------------------------------------------------------

  (1) Cache scaling proven.  The dedup cache key (OperationName,
      ResultType) scales beyond two distinct kinds. The 2-kind case
      (dual_quant_2d, multi_consumer_cat_2d) is extended to 3-kind
      without modification to the pass; runOnce +
      applyMultiConsumerOptimization handle the extra entry naturally.
      The TTIR has exactly 3 typed cats with no false sharing.

  (2) FpToFpOp clone path verified end-to-end.  The triton::FpToFpOp
      branch of createSizeReducingClone, including the `getRoundingAttr()`
      carry-through, is exercised by the fp8e5 consumer. Bit-exactness
      across all 4 shapes confirms the rounding mode (rtne) survives
      the rewrite.

  (3) First fp8 output in the suite.  Bit-exact match across OFF/ON for
      the fp8e5 output (rendered via torch.float8_e5m2) extends the
      pass's value-preservation guarantee to an additional dtype family.

  (4) Model generalization.  The DRAM-bandwidth attribution model from
      speedup_explaination.txt Part 8 generalizes from 2-chain to
      3-chain fan-out, both in the win direction (77% explained at
      1.60x) and in the regression direction (70% explained at 0.79x).
      Two new rows feed the cross-config consistency table.

  (5) Regression signature scales as predicted.  The pass's known
      regression family (heavy-spill diamond) becomes WORSE with 3
      chains than with 2: 0.79x at 3-kind vs 0.68x at 2-kind dual_quant
      (NB: different tile counts, but same mechanism).  This is
      evidence the regression cost scales roughly linearly with the
      number of cloned chains -- a constraint on the future B8
      register-pressure heuristic.

13. ONE-PARAGRAPH SUMMARY
--------------------------------------------------------------------------------

A1 extends DowncastReorderOptimizer's multi-consumer dedup cache test from 2 to 3
distinct OperationName values fanning out from one fp32 tt.cat. With
{arith.fptosi -> i8, arith.truncf -> fp16, tt.fp_to_fp -> fp8e5}, the
cache produces exactly 3 typed cats in the rewritten IR (no false
sharing), bit-exactly preserves all three output tensors across the
OFF/ON toggle on 4 shapes including the fp8 path, exercises the
previously untested triton::FpToFpOp clone branch (including its
getRoundingAttr carry-through), and produces a perf landscape (8 wins,
6 neutrals, 4 regressions across 36 configs) whose magnitudes are
explained at 70-101% by the same DRAM-bandwidth model used for the
2-chain experiments. The regression at (256, 128) on 8192² is the
expected scaling of the 2-chain regression family -- the pass clones
N chains, each of which can independently spill, so the regression
worsens roughly linearly in N when neither chain fits in registers.
This experiment is the first kernel in the suite to (a) produce fp8
outputs, (b) verify the fp_to_fp rounding-mode-preservation path, and
(c) test the dedup cache with > 2 distinct keys.
