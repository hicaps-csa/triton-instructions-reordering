================================================================================
  deep_chain_2d @ M=N=8192, BLOCK_M=128, BLOCK_N=256 (WIN config)
  Spill-removal pass: verification & attribution write-up
================================================================================

Chain: load(a,fp32), load(b,fp32) -> reshape -> reshape -> cat -> reshape
       -> trans -> fptosi(i8) -> store

Pass behavior: sink fp32->i8 trunc past the 4-deep mover chain so the chain
runs in i8 instead of fp32.

Compare to cat_trunc_2d MID: that pass reduced shmem/barriers by 2x. Here
they are reduced by 4x because the chain has 4 movers (reshape -> cat ->
reshape -> trans), each of which forced a shared-mem round-trip in OFF mode.

================================================================================
8.  CAN WE DETERMINISTICALLY CONCLUDE THIS?
================================================================================

For deep_chain WIN, the answer is closer to "yes" than for cat_trunc MID,
because:

  (a) NEUTRAL (64, 64) is a clean control with identical DRAM, identical
      instructions, identical sha256, and identical duration. The pass does
      nothing when there is nothing to fix. This proves the pass cannot
      *introduce* a speedup absent spills.

  (b) 88% of the per-warp instruction delta at WIN is literally spill
      load/store opcodes. The "spills cause the slowdown" story is
      directly visible in the SASS diff.

  (c) 83% of the wall-time delta at WIN is accounted for by the saved DRAM
      bandwidth alone, computed as (3.49 GB saved) / (542 GB/s on ON).

  (d) The remaining 17% time and 12% inst delta is consistent with the 4x
      shared-mem and barrier reductions, which are a coupled side effect of
      the same IR rewrite that removes the spill.

DETERMINISTIC:
  - Bit-exactness (sha256).
  - Same algorithmic global I/O (SASS LDG/STG/F2I).
  - Same launch config.
  - Spill ops dominate the inst delta (88%).
  - DRAM-saved time dominates the wall-time delta (83%).
  - NEUTRAL control shows the pass has no effect without spills.

NOT DETERMINISTIC (still inferential):
  - The exact partition of the 17% residual time between "fewer barriers",
    "fewer LDSM/STS", and "fewer IMAD.MOV". These coupled mechanisms still
    can not be cleanly separated without a hand-written intermediate
    variant.

So compared to cat_trunc MID (where spill explains only ~25% of inst delta
and ~65% of time delta), deep_chain WIN is a much cleaner case: most of the
speedup is straightforwardly bandwidth savings from removed spill traffic.


================================================================================
9.  WHY THE NUMBERS ARE SO MUCH MORE DRAMATIC THAN cat_trunc
================================================================================

Three reasons:

  (1) Larger live range. The 4-mover chain holds more values live across
      more shuffles, so the spill set is bigger. OFF spills 27.6M reqs vs
      cat_trunc OFF's 1.87M reqs (~15x).

  (2) L1 is overwhelmed. With 14M spill requests bouncing through L1 over
      9 ms, the reuse window is destroyed; ~99% of spill bytes hit DRAM.
      In cat_trunc, only 60% reached DRAM. This is a function of working
      set size vs L1 capacity.

  (3) More movers to collapse. The pass replaces 4 shared-mem-staged
      movers with register/permute movers, hence the 4x BAR/LDSM/STS
      reduction (vs cat_trunc's 2x for a single mover).

The net effect is that for deep_chain at WIN, spill removal is both
mechanically (88% of inst) and quantitatively (83% of time) the dominant
cause of the speedup.
