================================================================================
  deep_chain_2d @ M=N=8192, BLOCK_M=128, BLOCK_N=128
  Spill-removal pass: verification & attribution write-up
================================================================================

Chain: load(a,fp32), load(b,fp32) -> reshape -> reshape -> cat -> reshape
       -> trans -> fptosi(i8) -> store

Selected because:
  - 1.19x speedup at M=N=8192 (smaller than WIN's 7.31x; "mild win")
  - Compiled OFF *does* spill (255 regs, 42 spill slots), so the pass has
    real work to do, but the spill set is ~40x smaller than WIN's.
  - Lets us check whether the same mechanism scales linearly with spill
    volume.

Inputs:
  - test_deep_chain_2d.py
  - nsys_results_2d.txt   (existing 128x128 row: OFF=1448us, ON=1219us)
  - /tmp/verify_deep_chain/{OFF_128x128, ON_128x128}/*
  - /tmp/verify_deep_chain/time_128x128.py (local CUDA-event timer)

Unchanged (algorithm preserved):
  - LDG.E.128.SYS (global reads): 64 == 64
  - STG.E.128.SYS (global writes): 16 == 16
  - F2I.S16.TRUNC.NTZ (truncations): 256 == 256
  - LOP3.LUT (math): 308 == 308

Eliminated:
  - All 67 spill ops (LDL.LU + LDL.LU.64 + STL + STL.64) gone
  - 28 IMAD.MOV.U32 ops (spill address arithmetic) gone

Reduced 4x (the chain's mover collapse):
  - BAR.SYNC, LDSM.16.M88.4, STS.128 all drop by 4x

Doubled:
  - PRMT (warp-level permutes that replace shmem staging)

Structural pattern is IDENTICAL to WIN (128x256): same 4x mover collapse,
same 2x PRMT, same spill-elimination shape - just at smaller absolute
counts. The pass behaves the same way; only the magnitude differs.

  All in expected directions:
    - lg_throttle drop: spill / local-memory LSU contention removed.
    - barrier drop: 4x fewer BAR.SYNC instructions (matches SASS).
    - short_scoreboard drop: less shmem-dependent waiting.
    - long_scoreboard rise: with the spill-induced LSU stalls gone, warps
      now expose the real global-memory load latency. This is the desired
      end state - the kernel is bound by what it MUST wait for, not by
      what we forced it to wait for.
    - math_pipe_throttle small rise: PRMT (more permutes) goes through
      math pipes.

7.  COMPARISON ACROSS THE THREE CONFIGS WE'VE NOW VERIFIED
================================================================================

                                cat_trunc MID   deep_chain 128x128   deep_chain WIN
                                (128x128)       (128x128)            (128x256)
  --------------------------------------------------------------------------------
  Speedup                       1.28x           1.19x                7.31x
  OFF regs                      255             255                  64
  OFF spills (compiler)         46              42                   916
  Spill reqs (ncu LD+ST)        1.87M           ~1.1M (analytical)   27.6M
  Spill DRAM observed           146 MB          (~120 MB est)         3.49 GB
  L1 absorbs                    ~60% of spill   ?                     ~1% of spill
  Wall-time delta               409 us          228 us               7777 us
  Per-warp inst delta           357             95                   3171
  Spill share of inst delta     ~25%            ~70% (before PRMT)   88%
  Bandwidth saved share of      ~65%            ~consistent (calc'd) 83%
    wall-time delta
  BAR.SYNC reduction            2x              4x                   4x
  LDSM/STS reduction            2x              4x                   4x
  PRMT change                   +2x             +2x                  ~+2x
  Bit-exact                     YES             YES                  YES

Pattern:
  - cat_trunc MID has ONE mover (the cat) -> 2x cut in shmem/barriers.
  - deep_chain has 4 movers -> 4x cut in shmem/barriers in both 128x128
    and 128x256.
  - The 7.31x WIN speedup comes from the spill set being 25x larger AND
    L1 being unable to absorb it -> DRAM bandwidth becomes the dominant
    cost. The 128x128 spill set is small enough that the speedup is
    modest, but the *mechanism* the pass uses is the same.

This is strong evidence that the pass implements a single transformation
("collapse the mover chain through registers + PRMT, eliminating spills
and shared-mem staging as coupled effects") and its measured speedup
varies with how much spill traffic that transformation removes.


================================================================================
8.  DETERMINISM ANALYSIS (after ncu measurement)
================================================================================

DETERMINISTIC for 128x128:
  - Bit-exact output (sha256 match).
  - Same algorithmic global I/O (LDG=64, STG=16, F2I=256 in both).
  - Same launch config (num_warps=4, num_stages=3, grid=4096).
  - SASS per-warp inst delta prediction (95) matches ncu (94) to 1%.
  - DRAM bytes saved (110 MB) is consistent with ncu's spill request
    upper bound (176 MB) minus the ~39% absorbed by L1.
  - Stall reasons shifted in all predicted directions.
  - DRAM-saved time (200 us) explains 84% of wall delta (238 us).
  - L1 absorption rate (39%) is intermediate between WIN (1%, L1 over-
    whelmed) and cat_trunc MID (60%, L1 ample), as expected from working
    set size.

INFERENTIAL still:
  - The 16% time residual (38 us) cannot be cleanly partitioned between
    "fewer barriers", "fewer LDSM/STS", and "fewer IMAD.MOV". These
    coupled mechanisms still cannot be separated without a hand-written
    intermediate variant.

Cross-config consistency proof (this is the strongest evidence so far):

  Config              Spill DRAM     ON BW         Predicted     Wall delta   Explained
                      saved          (GB/s)        cost (us)
  -------------------------------------------------------------------------------------
  cat_trunc MID         146 MB        543          269           409          66%
  deep_chain 128x128    110 MB        549          200           238          84%
  deep_chain WIN       3490 MB        542         6436          7777          83%

  The "DRAM bandwidth saved" model under-predicts wall delta in every
  case (because some non-DRAM cycles are also saved -- barriers, smem,
  inst), but it captures 66-84% of the speedup across three independent
  configs with different tile sizes and different kernels. This is a
  robust attribution: the dominant mechanism is spill DRAM bandwidth,
  with shmem/barrier reductions as a coupled but smaller contribution.
