WHAT DowncastReorderOptimizer DOES
-------------------------------------------------------------------------------
  Optimization: push size-reducing element-wise ops (truncf, trunci,
  fptosi, fptoui, narrowing fp_to_fp, narrowing index_cast) BEFORE
  data-movement ops.

  Pattern (before):
      %big   = tt.cat %a, %b : tensor<Nxf32> -> tensor<2Nxf32>
      %small = arith.fptosi %big : tensor<2Nxf32> to tensor<2Nxi8>

  Pattern (after):
      %a_i8  = arith.fptosi %a : tensor<Nxf32> to tensor<Nxi8>
      %b_i8  = arith.fptosi %b : tensor<Nxf32> to tensor<Nxi8>
      %small = tt.cat %a_i8, %b_i8 : tensor<Nxi8> -> tensor<2Nxi8>


SAFE DATA-MOVEMENT OPS HANDLED
-------------------------------------------------------------------------------

  triton::ReshapeOp, triton::ExpandDimsOp, triton::JoinOp,

DAG-HANDLING EXTENSIONS (most recent session)
-------------------------------------------------------------------------------
  Three capabilities added to handle non-trivial DAG patterns:

  (A) Diamond / partial-fanout support
      eligibleReducers() now FILTERS to size-reducing users instead of
      bailing when a non-reducer user exists. The original mover stays
      alive for non-reducer consumers (use_empty()-guarded erase in
      applyMultiConsumerOptimization). Cost: the mover may be duplicated
      (one rewritten i8 path + the original fp32 path).

  (B) In-pass chain propagation via worklist
      runOnce now uses llvm::SmallSetVector seeded by an initial walk,
      with upstream re-queueing after every rewrite. After rewriting a
      producer, every defining op of its operands that's itself a safe
      mover is added back to the worklist. Net effect: chains like
      Cat -> Trans -> Truncate or Reshape -> Cat -> Truncate collapse
      in a single runOnce instead of needing one outer iteration per
      chain layer.

  (C) Multi-reducer-kind fanout
      Already handled by applyMultiConsumerOptimization's
      DenseMap<pair<OperationName, Type>, Value> cache. A producer
      feeding e.g. one truncf-to-fp16 and one fptosi-to-i8 gets one
      rewritten chain per (kind, type) pair, with reducers of the same
      (kind, type) sharing.

  Outer fixed-point loop kept (capped 16 sweeps) as belt-and-braces.

-------------------------------------------------------------------------------
  Added the (128, 128) tile -- "mid" between neutral and win. The new
  results expose a sub-cliff regime that the original 3-config sweep
  missed: a measurable spill at (128, 128) that the pass kills entirely.

      Config    Pass    Dur us   Reg    Occ %   DRAM %    Spill LD    Spill ST
      neutral   OFF    1515.39    80    73.1    80.9          0           0
      neutral   ON     1516.48    66    86.0    81.1          0           0
      mid       OFF    1886.34   255    24.1    77.1     933.9K      933.9K   <-- new
      mid       ON     1477.34   218    24.8    83.7          0           0   <-- new
      win       OFF    9381.28    64    94.1    73.7      14.5M       14.8M
      win       ON     2436.61   255    24.3    78.0       2.0M        2.0M
      big       OFF    9925.86    64    88.6    70.4      14.6M       15.0M
      big       ON     8710.08    64    89.9    68.8      12.3M       12.4M

  Speedups (pass OFF / pass ON):
      neutral 1.00x   mid 1.28x   win 3.85x   big 1.14x

  MID story is interesting: even pass-OFF picks 255 regs/T (max), so
  it can't trade occupancy for fewer spills -- it just spills ~1.87M
  times anyway. With pass ON, the fp16 working set fits and spills
  drop to zero. Speedup is modest (1.28x) because the spill volume at
  this tile is small enough that DRAM time still dominates (DRAM goes
  77% -> 84%, not as dramatic as the win case's 73% -> 78%).

PROPOSED COMPLEX-DAG TEST KERNELS (not yet implemented)
-------------------------------------------------------------------------------
  Five kernels suggested to exercise the new DAG capabilities. Each is a
  small variant of the cat_quant_2d harness and can reuse its sweep/ncu
  scripts with minor tweaks. Status: only described, not yet written.

  1. Deep chain  --  Reshape -> Cat -> Reshape -> Trans -> Trunc
     Tests : in-pass chain propagation for a 4-deep mover chain. After
             one runOnce the trunc should land on the original loads.
     Watch : whether outer fixed-point iteration still hits 1 sweep.

  2. Diamond residual  --  cat result feeds both fptosi AND mulf
     Tests : diamond / partial-fanout (this is the case the strict pass
             would have skipped entirely).
     Expect: i8 cat for the quant path PLUS original fp32 cat kept alive
             for the multiply. Both paths coexist post-pass.
     Diag  : prime candidate for measuring whether duplication is worth
             it -- if ON loses to OFF here, that motivates a cost heuristic.

  3. Dual-precision quantize  --  cat result feeds (fptosi i8) AND (truncf f16)
     Tests : multi-reducer-kind dedup cache (OperationName, Type) keyed.
     Expect: TWO rewritten chains -- one fptosi-clones+i8 cat, one truncf-
             clones+f16 cat. Original fp32 cat dies.

  4. Diamond + chain combined  --  cat with reducer AND non-reducer users,
     where the reducer side has upstream reshapes
     Tests : worklist's upstream re-queue works correctly when the head
             of a chain is also the head of a diamond.

  5. Splat-quantize  --  scalar -> tt.splat -> trunc to i8
     Tests : scalar-operand path in createTransformedDataMovement (uses
             isIntOrIndexOrFloat() branch when operand is non-tensor).
     Expect: trunc operates on the *scalar* before the splat; splat then
             materializes i8 directly.

  Implementation pattern: copy cat_quant_2d harness into
  /home/pushpendram/triton_kernels/<name>_2d/, swap kernel body, reuse
  run_nsys_sweep_2d.sh and run_ncu_sweep_2d.sh with minor edits.
