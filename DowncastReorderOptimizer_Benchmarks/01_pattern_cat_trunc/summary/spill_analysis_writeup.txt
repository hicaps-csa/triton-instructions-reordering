================================================================================
2.  HOW TO PROVE THE SPEEDUP IS FROM SPILL REDUCTION (original 7 steps)
================================================================================

The compact summary is suggestive but not airtight. To nail it down:

  (1) Diff the SASS. cuobjdump --dump-sass on both kernels and confirm the
      only deltas are LDL/STL (local memory) ops + their address arithmetic.
      If you see different LDG/STG, different IMAD/FFMA mixes, or reordered
      tile loops, then something else also changed.

  (2) Check the instruction-count math. Removed inst = 5,849,088.
      Spill removed = 1,867,776 reqs. Each spill round-trip = LDL + STL +
      address calc + maybe a dependent move -> ratio of ~3.1 inst per spill
      req, which lines up. If the ratio is way off, something else got
      optimized.

  (3) Confirm identical I/O. Same grid, same block, same total bytes loaded
      from global. ncu's dram__bytes_read.sum and dram__bytes_write.sum should
      match between OFF/ON within noise.

  (4) Bit-exact output check. Run both kernels on the same input and
      torch.equal the outputs.

  (5) Lock the launch config. Set num_warps, num_stages, and any autotuner-
      controlled params explicitly so the only difference between runs is the
      pass.

  (6) Subtract the spill cost analytically. OFF spent X cycles on LDL/STL
      (~ stall_lg_throttle + a fraction of long_scoreboard). If
      OFF_duration - spill_cost ~ ON_duration, the speedup is fully accounted
      for by spill removal.

  (7) Stall-shift sanity. ON should show less lg_throttle and less
      short_scoreboard (it does). It can show more long_scoreboard (it does -
      11k -> 24k) because the warps are no longer artificially serialized by
      the spill-induced LSU contention; they expose the real global-memory
      latency, which is fine.

================================================================================
5.  REFINED STORY
================================================================================

The headline "speedup is from spill removal" is half right. The pass eliminates
all 1.87M spill requests, but it does so by RESTRUCTURING THE CAT-TRUNC
LOWERING to use warp-level shuffles (PRMT) instead of a shared-memory
round-trip. That restructuring also:
  - halves shared-memory traffic (STS.128/LDSM.16: 64 -> 32 each per thread)
  - halves __syncthreads barriers (127 -> 63 per thread)
  - removes the 146 MB of spill DRAM traffic that L1 couldn't absorb

So the correct claim is:

    "The pass replaces a shared-memory-staged, register-spilling cat lowering
    with a register/permute-staged lowering; the headline metrics that move
    (spill, BAR.SYNC, LDSM/STS, DRAM bytes) are all downstream of that single
    structural change."

Bit-exactness and identical LDG/STG/F2F counts prove the user-visible
computation is unchanged.


================================================================================
6.  CAN WE DETERMINISTICALLY CONCLUDE THIS?
================================================================================

No - and here is the precise distinction.

DETERMINISTIC CONCLUSIONS (things measurement + SASS proves outright):

  (a) Same function computed.
      torch.equal(OFF, ON) == True, 0/134M differing elements.
      The pass does not change what the kernel computes.

  (b) Same algorithmic global I/O.
      SASS opcode counts for LDG.E.128 (64), STG.E.128 (32), and
      F2F.F16.F32 (256) are identical. The kernel loads the same bytes from
      global, writes the same bytes back, and performs exactly the same number
      of fp32->fp16 conversions in both versions.

  (c) Same launch config.
      num_warps=4, num_stages=3, grid=4096, BLOCK_M=BLOCK_N=128.
      Compiled-side regs/spills (255/46 vs 218/0) match ncu exactly.

  (d) Pass restructured the cat lowering, not the surrounding tile code.
      The only opcodes whose counts changed are the ones involved in routing
      data through the cat operation (LDL/STL/STS/LDSM/PRMT/BAR.SYNC/LOP3/
      IMAD.SHL). Math and global I/O are byte-identical.

CAUSALLY INFERENTIAL (not deterministic):

  (e) "The speedup is from spill removal."
      Falsified as a standalone claim - spill removal is one of several
      coupled effects of a single IR rewrite (also fewer barriers, halved
      shared-mem traffic, more PRMT, less DRAM traffic).

  (f) "X% of the 409 us delta comes from spills, Y% from barriers, Z% from
      shared-mem."
      Not deterministically attributable from the data we have. The mechanisms
      are tangled because they are all consequences of one structural change.
      The 268 us of saved DRAM time + ~140 us residual is consistent with the
      story but does not prove the decomposition.

WHY WE CANNOT DECOMPOSE DETERMINISTICALLY:

The pass performs a single atomic IR rewrite that produces all four downstream
effects simultaneously. To isolate them, you would need to vary one at a time
- but you cannot toggle "remove spills without changing barrier count,"
because in this kernel the spills ARE the barriers (the cat goes through
shared mem; less staging means both fewer LDL/STL and fewer BAR.SYNC).

CLOSEST APPROACHES TO A DETERMINISTIC ATTRIBUTION (increasing rigor):

  (1) Roofline argument.
      ON's effective DRAM rate is 543 GB/s on a 2080Ti (peak ~616 GB/s) -
      i.e., ON is at ~88% of bandwidth roof. There is no headroom for a
      different compiler trick to make it materially faster on this hardware.
      So OFF is slower because it spends cycles NOT on bandwidth - and ncu's
      pipeline-cycle breakdown will show those cycles in LSU (spill traffic)
      + barrier waits + SMEM ops. This BOUNDS the attribution: "the extra
      time in OFF is entirely cycles spent on the mechanisms we removed;
      there is no missing third cause."

  (2) Per-pipeline cycle counters.
      Re-collect with sm__pipe_lsu_cycles_active.avg.pct_of_peak,
      smsp__cycles_active_pipe_*, and the per-warp-stall CYCLES (not raw
      stall counts). These attribute kernel time to pipelines, and you can
      subtract per pipeline OFF vs ON. That moves "spill cost ~ 268 us" from
      "consistent in magnitude" to "directly measured."

  (3) Controlled isolation.
      Hand-write three Triton variants:
        (a) status-quo OFF (spills + barriers + shared-mem stage),
        (b) shared-mem stage but no spill (raise maxnreg or hand-shrink the
            live range so it fits in 218 registers without changing the
            lowering),
        (c) pass ON (no spill, no shared-mem stage, more PRMT).
      Then (a)->(b) measures spill cost alone and (b)->(c) measures
      restructuring cost alone. This is the only way to truly decompose, and
      it requires real work to construct (b).

Without one of those, the strongest deterministic statement is the one in
items (a)-(d) above. The decomposition into "spill vs. barrier vs. SMEM" is a
coherent and quantitatively consistent story, but it is a model, not a proof.


================================================================================
7.  WHY L2 THROUGHPUT BARELY MOVED DESPITE THE SPILL DELTA
================================================================================

L2 thrpt: 28.65% (OFF) -> 30.18% (ON). Three reasons:

  (1) Spill bytes are tiny next to real bytes.
      1.87M spill reqs x ~128 B/warp = ~240 MB over 1.88 ms ~ 127 GB/s of
      LOCAL traffic. The kernel is moving multi-hundred-MB tensors of real
      data per launch, dominating L2/DRAM totals. Removing the spill changes
      the L2 budget by a few percent - which is what you see (28.65 -> 30.18).

  (2) Local memory hits L1, not L2.
      Spill slots are per-thread and accessed with extreme reuse (same warp
      keeps reading/writing the same offsets). On modern GPUs L1 (unified
      with shared) absorbs nearly all of that. Only L1 misses reach L2, and
      for tightly-reused spill slots the miss rate is low. So L2 hardly saw
      the spill traffic in the first place - removing it does not change L2's
      reading much.

  (3) L2% rises slightly anyway because the kernel got faster.
      L2 throughput is bytes/sec normalized to peak. The denominator (time)
      shrank, so even with the same useful global-data traffic going through
      L2, utilization ticks up. Same logic explains DRAM% rising 77% -> 84%:
      real data bytes are roughly constant; the kernel just processes them
      in less time.

Note: in this kernel, our measurement showed that the spill writes DID partly
reach DRAM (116 MB write delta). So claim (1) is more accurate as "spill
WRITES partly missed L1 and reached DRAM; spill READS were largely absorbed
by L1." Net L2 impact stays small either way.
